# Queue module review

Scope: module review of `src/queue.ts`, following its caller in `src/caller.ts`, against `PROJECT.md` and `API.md`. Applied `supplied-skill/SKILL.md` and its bundled evidence reference. `legacy.ts` is excluded from findings. The highest risk is that the queue reports completion without owning save completion or failure. No source or configuration was modified.

## P1 — Await each save and propagate its failure

**Location:** `src/queue.ts:9`.

`forEach` discards the promises returned by its async callbacks. With two selected jobs and deferred saves, both saves start immediately and `runQueue` resolves while neither save is complete. With a rejecting first save, `runQueue` still fulfills, the second save starts, and the first failure becomes an unhandled rejection. This violates the API requirements for sequential saves, completion, and stopping on failure. `src/caller.ts:3–4` trusts this promise before returning `'finished'`; its current `'0'` argument reaches saves because of the separate limit defect below. Fixing that limit does not repair positive-limit calls to the public queue API.

**Executed evidence:** a two-job invocation with limit `'2'` resolved with `started = ['a', 'b']` and `completed = []`. A separate invocation whose first save rejected with `Error('save failed')` yielded `queueRejected = false`, `started = ['a', 'b']`, and an observed `unhandledRejection` carrying that same error. The probe temporarily observed that event to capture the failure safely.

**Minimal remedy:** replace `selected.forEach(...)` with `for (const job of selected) { await save(job); }`. Preserve the original save rejection; do not swallow it or merely mark the callback promise as void. Add regression checks that keep the first save pending, ensure the second has not started and the queue has not resolved, then verify completion order; separately reject the first save and assert the queue rejects with the same error and never starts the second.

## P1 — Preserve the documented zero/pause limit

**Location:** `src/queue.ts:3`; affected caller: `src/caller.ts:3`.

`Number(raw) || 3` turns the valid string `'0'` into `3`. The settings UI's paused value therefore starts up to three saves. The supplied `submit` caller always passes `'0'`, so this is a directly exercised supported workflow, not a hypothetical input. A paused queue can persist jobs the user expected to leave untouched.

**Executed evidence:** `readLimit('0')` returned `3`; `await submit([{ id: 'a', priority: 1 }], save)` called `save` for `'a'` and returned `'finished'`.

**Minimal remedy:** default only when the argument is omitted, e.g. `raw === undefined ? 3 : Number(raw)`, so zero survives. The contract does not specify malformed-string handling, so this review does not prescribe a new validation or exception policy. Add checks for `'0'`, omitted input, and a positive integer string, including an assertion that a paused submission invokes no saves.

## P2 — Sort a copy of the caller-owned jobs array

**Location:** `src/queue.ts:8`.

`jobs.sort(...)` mutates the input before `slice` selects jobs. Passing jobs in order `['b', 'a']` with priorities `[2, 1]` permanently changes that caller-owned array to `['a', 'b']`, even when only one job is selected. `submit` passes its own caller's array through without copying (`src/caller.ts:3`), so the changed order is visible after submission. This violates the explicit ownership contract and can reorder the caller's UI/state independently of which jobs are saved.

**Executed evidence:** after `await runQueue(jobs, '1', async () => {})`, the same array changed from `['b', 'a']` to `['a', 'b']`.

**Minimal remedy:** use `[...jobs].sort((a, b) => a.priority - b.priority).slice(...)`. Retain the existing ascending numeric comparator. Add a regression check that saved jobs follow numeric priority while the original array and job references stay in their original order, including for a paused invocation.
