# Queue review

Scope: `src/queue.ts` and its caller, assessed against `PROJECT.md` and `API.md`. No source or configuration changes. `legacy.ts` is outside the review scope.

## Findings

1. **P1 — Saves are concurrent, completion is premature, and failures escape the returned promise** — `src/queue.ts:9`.
   `forEach` discards the async callbacks' promises. With two selected jobs and deferred saves, both saves start and `runQueue` resolves before either finishes. If the first save rejects, the second still starts, `runQueue` resolves successfully, and the failure becomes an unhandled rejection. Callers awaiting completion cannot reliably report success or catch save errors; Node's default handling can terminate the process.
   **Minimal remedy:** replace the async `forEach` with a sequential `for...of` loop containing `await save(job)`. Let failures propagate through the existing promise exception convention. Check deferred completion, maximum concurrency of one, and rejection preventing subsequent saves.

2. **P1 — Paused queues execute jobs** — `src/queue.ts:3`; concrete caller: `src/caller.ts:3`.
   `Number('0') || 3` evaluates to 3. `submit` always passes `'0'`, so it starts up to three saves despite the documented pause setting. The runtime probe with one job confirmed a save and a `'finished'` result.
   **Minimal remedy:** default explicitly when `raw` is `undefined`, preserving numeric zero (for example, `raw === undefined ? 3 : Number(raw)`). Keep any separate invalid-input policy explicit; the API does not specify one. Check omitted, zero, and positive integer string limits, including the caller's paused path.

3. **P2 — Selection mutates the caller's array** — `src/queue.ts:8`.
   `jobs.sort(...)` sorts in place even when only one job is selected. Input IDs `['3','1','2']` became `['1','2','3']` after a limit-one call. This violates caller ownership and can reorder UI or subsequent caller processing.
   **Minimal remedy:** sort a shallow copy for priority selection. Verify that the original array retains its element order after a call, including a paused call.

4. **P2 — Selected saves lose input order** — `src/queue.ts:8–9`.
   The API separately requires selection by ascending numeric priority and saves in input order. For input priorities `[2,3,1]` with limit `'2'`, the selected jobs are priorities 1 and 2, but their input order is `[2,1]`. The implementation starts saves in `[1,2]` order. Merely awaiting a loop over the current `selected` array would preserve this violation.
   **Minimal remedy:** select the lowest-priority entries using a copied list tagged with original indices, then restore original index order before the sequential save loop. Check selection membership and save order independently using unsorted input. Original indices also preserve distinct occurrences if the same job object appears multiple times.

## Checks actually run

- `npm run typecheck` — passed, exit 0.
- `npm test` — passed, exit 0; builds with the preinstalled TypeScript compiler and runs one test, covering only `readLimit()` returning 3.
- Inline Node ESM probes against the compiled queue and caller — passed all assertions confirming the defects above:
  - `readLimit('0')` returned 3; `submit` saved one supplied job and returned `'finished'`.
  - Two deferred saves both started; neither finished before the queue promise resolved.
  - First-save rejection did not reject the queue promise; both saves started. A temporary `unhandledRejection` listener captured the exact injected error.
  - Limit-one selection changed the supplied array from `[3,1,2]` to `[1,2,3]`.
  - Limit-two selection on `[2,3,1]` started saves in `[1,2]`, instead of selected input order `[2,1]`.

No network access, package installation, delegation, or global changes were used. Build output was generated by the project's test script; source and configuration were unchanged.
